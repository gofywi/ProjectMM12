BYTE — OFFLINE DOCUMENT SUMMARIZER
=============================================================================

PROJECT OVERVIEW:
Offline document summarization & chat app built with React Native for Android.
The user uploads a .docx, .pdf, or .txt file and the app produces a concise
summary / Q&A entirely on-device using the LiquidAI LFM 1.2B model (Q4_K_M
quantized), powered by llama.cpp via the llama.rn library. No internet
connection or cloud API is ever used.

Core flow:
  1. User picks a .docx, .pdf, or .txt from device storage
  2. App extracts plain text from the file (client-side, no server)
  3. Text is chunked if it exceeds the model's context window
  4. LFM 1.2B generates a summary for each chunk, then a final merged summary
  5. Summary / chat is displayed on-screen
  6. All chat sessions are persisted to SQLite and accessible via the
     in-app history drawer

  5. react-native-sqlite-storage - SQLite for chat session / message persistence
  6. @react-navigation/native           - React Navigation core
  7. @react-navigation/native-stack     - Native stack navigator
  8. react-native-screens               - Native screen primitive (peer dep of native-stack)
                                         Requires c++_shared CMake patch — see patch.txt

  Document parsing (native bridge — zero external deps):
    .pdf  — PdfTextExtractorModule.kt  (native Kotlin, Apache PDFBox)
    .docx — DocxTextExtractorModule.kt (native Kotlin, ZipInputStream + XmlPullParser)
            No Apache POI needed — uses Android built-ins only.
            Reads word/document.xml inside the OOXML ZIP archive.
            Handles paragraphs, line breaks, tabs, and tables (cells joined with " | ").
            Supports content://, file://, and absolute path URIs.
    .txt  — TxtTextExtractorModule.kt  (native Kotlin, raw byte read)
            Decodes as UTF-8; falls back to ISO-8859-1 for Windows-1252 files.
            Supports content://, file://, and absolute path URIs.

HOW IT WORKS — FULL FLOW
=============================================================================

### 1. App Launch
HomeScreen mounts and initializes the model:
  a) LlamaService.initialize()    - copies model.gguf from assets if needed,
                                    initializes llama.cpp context (~5-15s)
  b) DatabaseService.initialize() - opens byte.db, creates tables if needed,
                                    runs any pending migrations

  First launch: ~30s (model copy). Subsequent: 5-15s (model load).

### 2. Picking a Document
  a) User taps "Upload Document" button on HomeScreen
  b) @react-native-documents/picker opens the native file picker
     (filtered to PDF, DOCX, and TXT MIME types via DocumentService.pickDocument())
  c) DocumentService.extractTextFromDocument(uri, type) called:
       .pdf  → PdfTextExtractorModule.kt  (Apache PDFBox, native Kotlin)
       .docx → DocxTextExtractorModule.kt (ZipInputStream + XmlPullParser, no deps)
       .txt  → TxtTextExtractorModule.kt  (raw byte read, UTF-8/ISO-8859-1 fallback)
  d) Raw text returned and truncated to MAX_CONTEXT_CHARS (28 000 chars ≈ 7 000 tokens)
     to ensure it fits within the 32K context window alongside the system prompt

### 3. Chat Session
  a) User navigates to ChatScreen with documentText + documentName route params
  b) Header shows the document name badge
  c) Quick-action chips appear (Summarize / Key points / Explain)
  d) User sends a message → LlamaService.generateResponseStream() streams reply
  e) On first message, DatabaseService.createSession(title, documentName) is called
     — stores the session title (first message) and document_name in SQLite
  f) Every user + assistant message is saved via DatabaseService.saveMessage()

### 4. History Drawer
  Accessible via the ☰ menu icon in the ChatScreen header.

  Implementation:
    - Rendered inside a React Native Modal (transparent, animationType="none")
    - Using Modal avoids the Android useNativeDriver hit-test offset bug where
      translateX-animated views receive touches at their original off-screen position
    - Backdrop: full-screen Animated.View with pointerEvents="none" (visual only)
    - Close zone: TouchableOpacity covering only the area to the right of the drawer
    - Drawer panel: Animated.View sliding in from the left (spring animation,
      tension: 180, friction: 20 for fast settle)

  Session list row layout:
    [icon]  First message text (item.title, truncated)
            document_name (max 20 chars + …)  ·  N msgs

  Actions:
    - Tap row → loadSession(): loads messages from DB, restores chat state,
                               restores document name in header
    - Long-press → deleteSessionFromDB(): Alert confirmation + DB delete
    - ✏️ icon in drawer header → new chat (resets state, closes drawer)
    - × icon / tap backdrop area → closes drawer

### 5. Model Configuration

  Main Model (LFM 1.2B):
    n_ctx:        32768  (32K context window)
    n_gpu_layers: 0      (CPU-only for stability)
    use_mlock:    false

  Inference Parameters (src/provider/Parameter.ts):
    n_predict:      1024   (max summary tokens)
    temperature:    0.3    (low — factual, deterministic output preferred)
    top_k:          40
    top_p:          0.95
    min_p:          0.05
    xtc_threshold:  0.05
    xtc_probability:0
    typical_p:      1
    penalty_last_n: 64
    seed:           -1

=============================================================================
CHUNKING STRATEGY
=============================================================================

Problem: Documents frequently exceed the 32K context window once a system
prompt and output tokens are accounted for.

Strategy:
  CHUNK_SIZE_CHARS = 8000   (approx 2000 tokens at ~4 chars/token)
  TOKEN_BUDGET     = 28000  (32768 − system_prompt − output_reserve)

  DocumentService.chunkText(text):
    - Splits on paragraph boundaries (double newline) where possible
    - Falls back to character-limit split if a single paragraph is too long
    - Returns string[]

  If chunks.length === 1 → single-pass summarization
  If chunks.length  >  1 → map-reduce summarization:
      Pass 1: summarize each chunk independently (parallel or sequential)
      Pass 2: concatenate chunk summaries → final merged summary prompt

=============================================================================
SYSTEM PROMPT ARCHITECTURE
=============================================================================

  File: src/provider/SummaryTemplate.ts

  Single-purpose prompt — no persona system needed:
    "You are a precise document summarizer. Given the following document text,
     produce a clear, concise summary covering the key points. Do not add
     information not present in the document. Do not use bullet points unless
     they appear in the original. Keep the summary under 300 words."

  Merge prompt (used in multi-chunk pass 2):
    "You have been given partial summaries of sections of a longer document.
     Combine them into a single coherent summary under 400 words, preserving
     all key information and eliminating redundancy."

DATABASE SCHEMA
=============================================================================

Database: byte.db (SQLite, location: app databases/ directory)

Tables:

  sessions
    id             INTEGER PRIMARY KEY AUTOINCREMENT
    title          TEXT NOT NULL           (first user message, truncated to 100 chars)
    created_at     TEXT NOT NULL           (ISO 8601)
    updated_at     TEXT NOT NULL           (ISO 8601, updated on every new message)
    personality_id TEXT                    (reserved, unused in current build)
    document_name  TEXT                    (original filename — added via ALTER TABLE migration)

  messages
    id             INTEGER PRIMARY KEY AUTOINCREMENT
    session_id     INTEGER NOT NULL        (FK → sessions.id ON DELETE CASCADE)
    role           TEXT NOT NULL           ('user' | 'assistant')
    content        TEXT NOT NULL
    timestamp      TEXT NOT NULL           (ISO 8601)

  messages_fts   (FTS5 virtual table — optional, falls back gracefully if unavailable)
    Mirrors messages table for full-text search via MATCH queries.
    Kept in sync via INSERT/DELETE/UPDATE triggers.

  memories
    id             INTEGER PRIMARY KEY AUTOINCREMENT
    session_id     INTEGER NOT NULL UNIQUE (FK → sessions.id ON DELETE CASCADE)
    summary        TEXT NOT NULL
    metadata       TEXT NOT NULL           (JSON: { message_count, session_title })
    created_at     TEXT NOT NULL           (ISO 8601)

Indexes:
  idx_sessions_updated              ON sessions(updated_at DESC)
  idx_messages_session_timestamp    ON messages(session_id, timestamp)
  idx_memories_created              ON memories(created_at DESC)

Key design decisions:
  - document_name added as a nullable column via ALTER TABLE migration so existing
    installs are not broken (migration wrapped in try/catch)
  - createSession(title, documentName?, personalityId?) — documentName is the
    second argument and is stored in the document_name column
  - getAllSessions() returns document_name alongside message_count for the drawer

=============================================================================
KNOWN ANDROID GOTCHAS
=============================================================================

1. useNativeDriver + translateX hit-test offset bug
   When a view is animated with useNativeDriver: true and a translateX transform,
   Android's touch hit-testing uses the view's ORIGINAL (pre-animation) position.
   Result: a view that visually slides in is untouchable at its visual location.
   Fix: Render the animated drawer inside a <Modal transparent> — Modal creates a
   new Android Window where touch areas always match visual positions.

2. FlatList touch delay inside animated views
   FlatList has its own scroll pan-responder that competes with child TouchableOpacity
   presses, adding ~100-300ms latency on Android.
   Fix: Replace FlatList with ScrollView + .map() for short lists (history drawer).
